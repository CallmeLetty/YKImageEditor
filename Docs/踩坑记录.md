# 踩坑记录

本文档记录 YKImageEditor 开发和重构过程中遇到的问题、原因、无效尝试及最终处理方式。结论应以实际代码和验证结果为准；尚未完成的修复必须明确标记状态。

## 1. SwiftUI 重构后裁剪旋转状态异常

**状态：最终状态模型修复待实现**

### 1.1 问题表现

裁剪工具从 UIKit 页面重构为 SwiftUI 后，“旋转”出现以下异常：

- 第一次点击看起来是逆时针旋转 90°。
- 再次点击后图片回到原位，而不是继续旋转到 180°。
- 用户确认旧 UIKit 版本中没有该问题。

涉及代码：

- `Sources/YKImageEditorUI/SwiftUI/CropEditorView.swift`
- `Sources/YKImageEditorCore/ImageGeometry.swift`

### 1.2 原本的 UIKit 实现

旧实现由 `CropToolViewController` 持有裁剪状态：

```swift
private var workingImage: UIImage
private let imageView = UIImageView()

private func rotate() {
    workingImage = ImageGeometry.rotate90(workingImage, quarterTurns: 1)
    imageView.image = workingImage
    cropOverlay.resetCropRect(ratio: selectedRatio)
    view.setNeedsLayout()
}
```

它具有以下特点：

1. `CropToolViewController` 是裁剪会话期间长期存在的引用类型。
2. `workingImage` 是控制器实例属性，不依赖视图重建保持状态。
3. `UIImageView` 只更新 `image`，不会重新创建状态持有者。
4. 图片更新、裁剪框重置和布局刷新由控制器按固定顺序同步执行。

因此，UIKit 版本依赖一个稳定的命令式生命周期：按钮事件修改控制器中的图片，然后更新同一个 `UIImageView`。在原有使用场景中，连续旋转状态没有丢失或往返。

需要注意：旧实现同样直接把旋转结果写回 `workingImage`。它能正常工作不代表这种“用结果位图隐式表示旋转状态”的设计足够稳健，只是 UIKit 控制器生命周期掩盖了这个设计缺口。

### 1.3 SwiftUI 重构后的实现

SwiftUI 版本把裁剪状态移入 `CropEditorViewModel`：

```swift
@Published private(set) var workingImage: UIImage
@Published private(set) var resetID = 0

func rotate() {
    workingImage = ImageGeometry.rotate90(workingImage, quarterTurns: 1)
    resetID += 1
}
```

页面根据 `workingImage` 派生图片和裁剪区域：

```swift
Image(uiImage: model.workingImage)

let imageFrame = AVMakeRect(
    aspectRatio: model.workingImage.size,
    insideRect: CGRect(origin: .zero, size: proxy.size)
)
```

与 UIKit 版本相比，新的更新链路是：

1. 修改 `@Published workingImage`。
2. SwiftUI 重新计算 `body`。
3. 旋转导致图片宽高交换，`GeometryReader` 重新计算 `imageFrame`。
4. `CropOverlayRepresentable.updateUIView` 同时接收新的图片区域和 `resetID`，并重置裁剪框。
5. `Image(uiImage:)` 根据新的 `UIImage` 重新生成显示内容。

当前实现没有独立保存“已经旋转了几次”，而是从最新位图本身推断全部状态。图片既是编辑数据，又被当作旋转状态；SwiftUI 的声明式重绘、尺寸变化和 UIKit 裁剪桥接层更新全部耦合在一次赋值中，导致问题难以隔离，也容易出现状态往返。

### 1.4 为什么会有问题

问题由两个层面叠加造成。

#### A. 旋转状态没有独立建模

当前每次点击都对上一次生成的位图再次执行旋转：

```swift
workingImage = rotate90(workingImage, quarterTurns: 1)
```

这里没有 `quarterTurns` 作为唯一状态来源。只要位图生成、视图重建或图片方向解释中的任一环节不稳定，就无法判断当前应该显示 90°、180° 还是原图。

#### B. UIKit 与 Core Graphics 坐标系曾被混用

原 `ImageGeometry.rotate90` 在 `UIGraphicsImageRenderer` 中直接调用：

```swift
context.cgContext.draw(cgImage, in: drawRect)
```

`UIGraphicsImageRenderer` 使用 UIKit 左上原点坐标，而直接绘制 `CGImage` 使用 Core Graphics 图片语义。两者混用可能把额外镜像带入旋转结果，使第一次旋转方向错误，并让连续变换表现为往返。

这个底层问题能够解释错误方向，但由于旧 UIKit 页面使用同一核心方法且实际表现正常，它不能单独解释“仅 SwiftUI 重构后出现”的全部现象。SwiftUI 状态链路仍需独立修复。

### 1.5 已尝试但不足的修复

已把旋转绘制从：

```swift
context.cgContext.draw(cgImage, in: drawRect)
```

改为：

```swift
image.draw(in: drawRect)
```

这样可以统一 UIKit 绘制坐标系，避免直接绘制 `CGImage` 引入额外方向转换。但用户复测后确认问题仍然存在，说明这只是必要的底层修正，不是最终修复。

经验：不能因为一个底层实现明显可疑，就在没有复测的情况下把它认定为唯一根因。重构回归必须同时检查状态生命周期和显示链路。

### 1.6 最终修复方案

裁剪模型应保留不可变源图，并显式保存几何状态：

```swift
private let sourceImage: UIImage
@Published private(set) var quarterTurns = 0
@Published private(set) var isHorizontallyFlipped = false
@Published private(set) var isVerticallyFlipped = false
```

旋转按钮只修改状态：

```swift
func rotate() {
    quarterTurns = (quarterTurns + 1) % 4
    rebuildWorkingImage()
}
```

`rebuildWorkingImage` 始终从 `sourceImage` 和当前几何状态生成预览，不再对上一次生成的位图继续做破坏性变换。

正确的数据流应为：

```text
sourceImage
    + quarterTurns
    + horizontalFlip
    + verticalFlip
    -> 确定性的 workingImage
    -> SwiftUI 预览和裁剪框布局
```

该方案的原理是：

1. **单一事实来源**：旋转次数由 `quarterTurns` 表示，不通过观察位图猜测。
2. **幂等重建**：相同源图和相同状态永远生成相同结果，不受上一次渲染结果影响。
3. **隔离视图生命周期**：SwiftUI 可以任意重算 `body`，几何状态不会丢失。
4. **明确循环规则**：旋转状态只可能是 `0、1、2、3`，第四次才回到原位。
5. **便于撤销和测试**：历史记录只需保存轻量几何状态，不必为每次旋转保存完整位图。

如果旋转和翻转需要保持严格的操作顺序，应使用一个合并的几何变换状态或操作序列，而不是简单交换多个布尔值；因为“先翻转后旋转”和“先旋转后翻转”通常不是同一个结果。

### 1.7 必须补充的测试

最终修复至少需要覆盖：

- 非对称四色图片第一次旋转方向正确。
- 连续两次为 180°，不会回到原位。
- 连续四次才恢复原始方向。
- SwiftUI 重新计算页面后 `quarterTurns` 不变。
- 图片宽高交换时裁剪框更新，但旋转状态不重置。
- 旋转与左右/上下翻转按操作顺序得到正确结果。

在状态模型修复落地并由用户复测前，本条问题不能标记为“已解决”。

## 2. 液化预览比手势慢一帧以上

**状态：已改为 Metal 实时预览，待真机手感验证**

### 2.1 问题表现

进入液化工具后，笔刷圆圈能够立即跟随手指，但图片形变总是落后一点。连续快速拖动时，笔刷已经到达新位置，图片仍停留在前一次形变结果。

涉及代码：

- `Sources/YKImageEditorUI/SwiftUI/ImageEditorViewModel.swift`
- `Sources/YKImageEditorUI/Canvas/LiquifyMetalPreviewView.swift`
- `Sources/YKImageEditorCore/LiquifyDeformer.swift`
- `Sources/YKImageEditorCore/LiquifyProcessor.swift`

### 2.2 原本的实现

原本的液化预览和最终输出共用 `LiquifyProcessor.render`。每次手势更新都会请求在后台生成一张最长边为 `560px` 的新位图：

```swift
DispatchQueue.global(qos: .userInteractive).async {
    let preview = LiquifyProcessor.render(
        image: source,
        deformer: snapshot,
        maxDimension: 560
    )
    DispatchQueue.main.async {
        canvas.setPreviewImage(preview)
    }
}
```

一次预览需要完整执行以下工作：

1. 缩小源图。
2. 提取整张图片的 RGBA 数据。
3. 为目标图片分配新的像素缓冲。
4. 对每个目标像素插值形变网格。
5. 对源图片做双线性采样。
6. 重新创建 `UIImage`，然后回到主线程显示。

为了避免同时提交过多任务，旧实现用 `isLiquifyRendering` 和 `needsLiquifyRender` 合并更新。如果上一帧未完成，新手势只会把 `needsLiquifyRender` 设为 `true`，屏幕仍显示上一张已经完成的图片。因此它虽然限制了任务数量，却天然会让画面落后一个完整的 CPU 渲染周期。

手势结束时的 `force` 刷新还可能在旧任务未结束时再启动一个任务。旧结果可以通过 generation 丢弃，但旧计算无法真正取消，CPU 竞争反而可能加重延迟。

### 2.3 根因

液化是连续、高频的交互效果，预览必须在一帧预算内完成。60 Hz 屏幕每帧只有约 `16.7ms`，120 Hz 屏幕每帧只有约 `8.3ms`。

旧实现的问题不是后台队列优先级不够，也不是 SwiftUI 本身响应慢，而是把“最终位图生成”放进了“手势实时预览”链路。`userInteractive` 只能提高 CPU 任务调度优先级，不能把逐像素整图计算变成稳定的一帧内操作。

笔刷圆圈由 `CAShapeLayer` 直接移动，图片则等待 CPU 产生下一张 `UIImage`，两条显示链路耗时完全不同，所以用户会明确感受到二者不同步。

### 2.4 最终修复

预览和最终输出改为两条独立链路：

```text
手势
  -> 更新 LiquifyDeformer 的 57 x 57 位移网格
  -> 上传约 26 KB 网格数据
  -> Metal fragment shader 插值位移并采样源纹理
  -> 当前屏幕帧显示

点击“应用”
  -> 对 LiquifyDeformer 创建快照
  -> LiquifyProcessor 在后台生成全分辨率位图
  -> 提交到 EditorSession
```

具体处理：

1. 新增 `LiquifyMetalPreviewView`，源图只在进入液化工具时上传一次纹理。
2. `LiquifyDeformer.displacementVectors()` 按网格顺序导出反向位移，GPU 和 CPU 使用同一份形变语义。
3. 手势移动只更新约 `57 x 57 x 8 bytes` 的位移数据，不再提取和重建整张图片。
4. Metal fragment shader 对四个相邻控制点做双线性插值，再直接采样源纹理。
5. `MTKView` 使用按需绘制，同一屏幕刷新周期内的多次手势更新会自然合并为最新网格。
6. GPU buffer 在命令完成后回收，避免 CPU 覆盖仍被 GPU 使用的数据。
7. 撤销、重做和重置只恢复 `LiquifyDeformer` 快照并刷新 GPU，不生成中间位图。
8. 最终应用仍使用 CPU 全分辨率渲染，避免屏幕分辨率预览参与导出并降低结果质量。

### 2.5 修复原理

液化计算最适合 GPU：屏幕上的每个像素可以独立根据形变网格寻找源坐标，fragment shader 能并行处理这些采样。CPU 每次重建整张图片是串行的大量循环和内存操作；GPU 则保留源纹理，只替换很小的位移网格。

该方案也保持了历史模型的轻量化：撤销记录仍是操作前后的形变网格，而不是每一笔对应的一张位图。实时性能、撤销粒度和最终输出质量互不耦合。

### 2.6 回归验证

真机验证时应覆盖：

- 60 Hz 和 120 Hz 设备上连续快速拖动，图片与笔刷没有可感知的固定滞后。
- 横图、竖图和方图的笔刷位置与形变区域一致。
- 图片顶部拖动不会作用到底部，纹理没有上下翻转。
- 连续多笔后撤销只撤销最后一笔，重做能够恢复。
- 重置后画面恢复源图，且后续液化仍能继续操作。
- 点击应用后的全分辨率结果与 Metal 预览方向一致。
- 退出液化或切换工具后 Metal 预览层不会遮挡其他工具。

本次实现未进行构建和真机性能验证，因此不能仅凭代码完成就认定手感已经达标。
